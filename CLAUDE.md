# Holo Shadowing

Personal YouTube listening-practice app (single user). See [README.md](./README.md) for what it does and [docs/design.md](./docs/design.md) / [docs/adr/](./docs/adr/index.md) for the design record.

## Commands

```bash
pnpm install
pnpm test         # vitest — shared/chunker.ts only today
pnpm type-check    # vue-tsc for src/, tsc for worker/ (two separate tsconfigs, one command)
pnpm lint          # vp lint . --fix — close to vite-plus's own defaults, see Gotchas
pnpm format        # vp fmt .
pnpm build         # vite build; add VITE_DEMO_MODE=true VITE_BASE_PATH=/DictaTube/ to reproduce the GitHub Pages build locally (base path still uses the repo name, unchanged for now)
pnpm dev           # vite dev server
pnpm preview       # serves the last build through workerd — see Gotchas re: VITE_BASE_PATH
pnpm cf-typegen    # regenerate worker-configuration.d.ts after editing wrangler.jsonc — also runs on postinstall
```

## Directory Structure

```
.
├── src/                     # SPA (Vue 3 + TS), plain Vite convention — NOT Child's nested src/app/ (see ADR-004)
│   ├── views/               # kebab-case filenames — see Code Style; home-view/player-view/import-view/playlist-view
│   ├── components/          # small presentational components shared across views: video-list-item.vue, playlist-panel.vue (plain RouterLink rows, no drag handle markup), swipeable-item.vue (generic swipe-to-reveal-delete wrapper, no dependency, `disabled` prop lets a parent yield the gesture to Sortable mid-drag)
│   ├── demo-data.ts         # mock Video/Playlist/Chunk data + fake import/playlist/reorder/delete helpers, used only when VITE_DEMO_MODE=true
│   └── youtube-iframe-api.ts  # loads the YouTube IFrame Player <script> once, globally
├── worker/                  # single Cloudflare Worker, bundled by @cloudflare/vite-plugin (ADR-004)
│   ├── index.ts             # fetch(request, env, ctx) — routes by hand, then falls back to env.ASSETS.fetch()
│   ├── lib/ordering.ts      # nextTopPosition() — shared "insert at top" position-key helper for playlists/videos/playlist_videos
│   └── routes/              # one file per resource, not per HTTP method (unlike the old Pages Functions layout); videos/progress/playlists — no import.ts yet, see Key Files
├── shared/                  # chunker.ts + types.ts, imported by both src/ and worker/
├── db/schema.sql             # D1 schema (videos/chunks/progress/playlists/playlist_videos, all three ordering tables carry a `position` column); applied via `wrangler d1 migrations` (migrations_dir in wrangler.jsonc), not yet run against a real D1 instance
├── docs/design.md            # architecture + status, in Japanese
├── docs/adr/                 # one ADR per architectural decision, in English
├── wrangler.jsonc            # Worker name, D1 binding, assets binding — main points at worker/index.ts
├── worker-configuration.d.ts  # generated by `wrangler types`, gitignored — global `Env` interface, not hand-written
├── .github/workflows/gh-pages.yml         # dev-preview deploy (uploads dist/client), triggers on push to develop only
└── .github/workflows/deploy-production.yml  # production deploy to Cloudflare Workers, triggers on push to main (ADR-005)
```

`vite build` emits two things: `dist/client/` (static frontend) and `dist/holo_shadowing/` (bundled Worker + generated `wrangler.json` — `@cloudflare/vite-plugin` sanitizes the worker name's `-` to `_` for the build environment name, so this doesn't match `wrangler.jsonc`'s `name` literally). Don't assume `dist/` itself is the deployable output — it's always one of those two subdirectories.

## Key Files

- Change how captions are split into chunks: `shared/chunker.ts` (`parseJson3Captions`, `chunkWords`) — shared by the SPA and the Worker, keep it that way rather than duplicating logic.
- Toggle subtitle visibility, chunk-repeat, or play/pause: `src/views/player-view.vue` (`isSubtitleVisible`, `isRepeating`, `isPlaying`) — repeat re-seeks to the chunk start when playback crosses `chunk.endMs`, driven by the same poll loop as `togglePlayPause`'s plain play/pause. All controls live in the sticky bottom bar (two rows: prev/next, then CC / play / repeat), all three toggles share one on/off class ternary (`border-brand-500 bg-brand-500/10 text-brand-400` on, `border-transparent text-ink-muted` off) — don't reintroduce a different accent per button, that's the "styles are inconsistent" bug this was fixed from. The middle button's label is always the literal text "play", never "pause" — only its color reflects `isPlaying`; a state-dependent label was tried and rejected (user feedback: "the text is the problem, just always show play"). Nothing in the header is interactive besides the back link, and there's no per-chunk status indicator (removed on purpose, see `docs/design.md` セットアップ状況 — a video can have far too many chunks to represent as a dot per chunk). Seeking to a chunk's start only happens in `goToChunk` (prev/next); `togglePlayPause` never seeks, so resuming after pause continues from wherever playback stopped. The subtitle box always renders the same element/classes (fixed size) — only the `<span v-if="isSubtitleVisible">` text inside toggles, so hiding subtitles never resizes or reflows the box. The whole screen is `h-dvh overflow-hidden` (not `min-h-dvh`+scroll) with the subtitle box as the only `flex-1 min-h-0 overflow-y-auto` child, so normal-length chunks always fit one viewport with no page scroll; the box's own `overflow-y-auto` is just a safety net for an abnormally long chunk, not the intended UX.
- Add an API route: add a handler function to `worker/routes/*.ts` (plain `(db, ...) => Promise<Response>`, no framework-specific handler type) and wire it into `worker/index.ts`'s `routeApi`/`routeVideoDetail`/`routePlaylists` routing — there's no file-based routing here, unlike the old Pages Functions setup.
- D1 access inside the Worker is just `env.DB` (passed down as a plain `D1Database` argument to route functions) — query with `db/schema.sql`'s column names (snake_case in SQL, mapped to camelCase `shared/types.ts` shapes by small `toX` mapper functions in each route file). The `Env` type itself is global ambient, generated from `wrangler.jsonc` by `wrangler types` — there's no `worker/types.ts` to hand-edit; add a binding to `wrangler.jsonc` and run `pnpm cf-typegen`.
- Chunk-loop playback: `src/views/player-view.vue` + `src/youtube-iframe-api.ts`. Playback must only ever start from a user tap, never automatically — mobile browsers block autoplay otherwise.
- Playlists: `shared/types.ts`'s `Video.playlistIds` + `Playlist`, `worker/routes/playlists.ts` (list/create/delete playlist, list/add/reorder videos in a playlist), `db/schema.sql`'s `playlists`/`playlist_videos`. `src/views/home-view.vue` shows one panel per playlist (name + video count) plus a pinned, non-deletable "未分類" (unfiled) panel always rendered first, above the reorderable playlist list; tapping a panel navigates to `src/views/playlist-view.vue` (`/playlists/:playlistId`, `playlistId === "unfiled"` is the special case for videos with no playlist) which lists that playlist's videos.
- Ordering, search, delete: every playlist/video list (home's playlist panels, a playlist's videos, the unfiled list) defaults to newest-first via each row's `position` column (`worker/lib/ordering.ts`'s `nextTopPosition()` — new rows get `-Date.now()` so they sort first without touching existing rows) and can be reordered by long-pressing anywhere on the row — there's no dedicated drag handle. `vue-draggable-plus`'s `<VueDraggable>` (a Vue wrapper over SortableJS) is configured with `:delay="300"` + `:touch-start-threshold="5"` (no `handle` option), so SortableJS itself tells a hold-still-then-drag gesture apart from a quick swipe (its own threshold-based cancel-if-moved logic); `swipeable-item.vue`'s own swipe activation threshold (`SWIPE_ACTIVATION_PX = 10`) is deliberately larger than Sortable's, so on any real horizontal movement Sortable always yields first, before the swipe ever engages. As a second line of defense once Sortable has actually started dragging (post-delay), the parent view flips a `isReordering` ref on `@start`/`@end` and passes it to every `swipeable-item.vue` as `:disabled`, so the swipe code is fully inert for the duration of an active drag and can't fight over the pointer mid-gesture. Deleting a video (from any list) removes it from the whole library, not just one playlist (`DELETE /api/videos/:id`, cascades chunks/progress/playlist_videos). Each list also gets a plain substring search box, pinned to the bottom of the screen (not the header — see the header-height Gotcha below); reordering is disabled while a search filter is active (index ambiguity), delete still works. `@end` on `<VueDraggable>` persists the just-dropped order by POSTing the full id list to the matching `.../reorder` route (or the demo equivalent in `src/demo-data.ts`).
- Header height: every view's `<header>` is a fixed `h-14` (56px), same padding/border, regardless of content (`home-view.vue`'s bigger title, the back-link rows on the other three) — this is deliberate, so navigating between pages never shifts the header height. Don't let a future header redesign make one page's header taller/shorter than the others.
- Import UI: `src/views/import-view.vue` (URL input → playlist selection), reached via the floating `+` button on `home-view.vue`. There is no `worker/routes/import.ts` yet — real caption fetching is still the unresolved step-0 spike (`docs/design.md`); in demo mode `src/demo-data.ts`'s `runDemoImport` fakes it by extracting the video ID from the URL, in real mode the view calls `/api/import` and surfaces a "not ready" message if that 404s.

## Code Style

- User-facing docs (`README.md`, `docs/design.md`) and commit messages are Japanese; ADRs (`docs/adr/`) and this file are English; code identifiers are always English.
- Vue SFC and `src/`-level `.ts` filenames are kebab-case (`home-view.vue`, not `HomeView.vue`) by convention — not currently lint-enforced (see Gotchas), just keep matching the existing files.

## Tech Stack

- Frontend: Vue 3 + TypeScript + Tailwind 4, built with `vite-plus` (the `vp` CLI wraps Vite, oxlint, and oxfmt) + pnpm.
- Drag-reorder: `vue-draggable-plus` (thin Vue wrapper over SortableJS) — the only non-Vue runtime dependency in `dependencies`; everything else (search, swipe-to-delete) is hand-rolled to avoid pulling in more gesture libraries.
- Backend (prod only): a single Cloudflare Worker (`worker/`) bundled by `@cloudflare/vite-plugin`, not Cloudflare Pages Functions — see [ADR-004](./docs/adr/004-cloudflare-workers-vite-plugin.md) for why, and for what this deliberately does _not_ copy from `NCPD-Template-Child` (it doesn't use Nuxt; its nested `src/app/` is an AWS-CDK-monorepo convention that doesn't apply here).
- Data (prod only): Cloudflare D1, accessed as `env.DB` inside the Worker. GitHub repo holds source only, no data (`docs/adr/002`).
- Auth (prod only): Cloudflare Access + GitHub IdP, owner-only (`docs/adr/001`).
- Dev preview: GitHub Pages, mock data only, no backend (`docs/adr/003`) — only `dist/client` is uploaded there, never the Worker build.

## Testing

- `pnpm test` runs real `vitest` (not `vite-plus`'s own test runner — see Gotchas) against `shared/**/*.test.ts` only, via a standalone `vitest.config.ts`.
- No test currently exercises `worker/` or `src/`; `pnpm type-check` and a manual browser check are what's verified those so far.
- The chunker tests use synthetic word-timestamp fixtures, not real fetched YouTube captions (fetching real json3 captions is exactly what the still-unresolved step-0 spike would validate) — don't treat them as proof the real parser handles real caption quirks.

## Documentation Maintenance

- A change to the architecture, data model, or hosting/auth setup needs a new or updated ADR under `docs/adr/` plus a row in `docs/adr/index.md`, in the same change.
- `docs/design.md`'s セットアップ状況/実装ステップ sections describe what's actually done — update them whenever a step's status changes, don't let them go stale.
- `README.md`'s command list must match `package.json`'s `scripts` — update both together.

## Gotchas

- `vite.config.ts`'s `lint` block was originally copied from `NCPD-Template-Child`'s `site-sample`, which hand-sets `categories` to `error` across `correctness`/`style`/`restriction`. That forced a full rewrite to avoid ternaries, optional chaining, magic numbers, >10-statement functions, and non-kebab-case filenames — and two of those categories being `error` simultaneously created self-contradicting rule pairs (`--fix` flip-flopping between `oxc/no-rest-spread-properties` ↔ `eslint/prefer-object-spread`, and `eslint/no-undefined` ↔ `unicorn/no-typeof-undefined`). That explicit `categories`/`rules` block was later dropped in favor of `vite-plus`'s own defaults (`lint.options.typeAware`/`typeCheck`, no explicit `categories`) to get closer to zero-config. The code still happens to follow those stricter conventions, but **lint no longer enforces them** — don't assume a reintroduced ternary/magic-number/`?.`/PascalCase-filename will be caught.
- `lint.options.typeAware`/`typeCheck` type-checks `worker/` too, but only because `tsconfig.json` explicitly references `tsconfig.worker.json` (added alongside `tsconfig.app.json`/`tsconfig.node.json`) — without that reference the type-aware linter silently only sees `src/`. Verified by deliberately introducing a typo'd D1 method call and confirming `vp lint` caught it.
- `vite.config.ts`'s `staged: { "*": "vp check --fix" }` (a pre-commit hook) only actually runs because `package.json`'s `"prepare": "vp config --no-agent"` installs it (sets `core.hooksPath` to `.vite-hooks/_`, committed to the repo) — `--no-agent` is deliberate, since `vp config` without it also rewrites this file's agent-instruction content.
- `wrangler.jsonc` changes don't retroactively update `worker-configuration.d.ts` — it's gitignored and regenerated by the `postinstall`/`cf-typegen` script, so a fresh `pnpm install` picks up binding changes, but editing `wrangler.jsonc` mid-session needs an explicit `pnpm cf-typegen` before type-check/lint will see it.
- Don't add a top-level `devEngines.packageManager` field even though `vite-plus`'s own scaffold default does — verified it makes npm hard-fail (`EBADDEVENGINES`) on any `npx <pkg>` run from this repo (npm reads it as "this whole tree requires pnpm" and refuses), including things unrelated to `vp`. Stick with the plain `"packageManager": "pnpm@10.33.0"` field, which Corepack actually honors without this side effect.
- `vite-plus`'s bundled test runner (`@voidzero-dev/vite-plus-test`, exposed as `vp test`) crashes (`Cannot read properties of undefined`) when it loads `vite.config.ts`'s `defineConfig`. Real `vitest` + a separate plain `vitest.config.ts` sidesteps it; don't switch `pnpm test` back to `vp test` without confirming that's fixed upstream. Because of this, `vite.config.ts`'s `lint.rules` re-enables `vite-plus/prefer-vite-plus-imports` (vite-plus's own scaffold default — it was missing here for a while, an oversight, not a deliberate drop) but scopes it `off` via `lint.overrides` for `vitest.config.ts`/`shared/**/*.test.ts`, since those two deliberately import raw `vitest`/`vitest/config` instead of `vite-plus`/`vite-plus/test`.
- `package.json`'s `vitest` devDependency version should track whatever `vite-plus` itself bundles as its own `vitest` dependency (check `node_modules/vite-plus/package.json`) — letting it drift behind (e.g. `^3.x` while `vite-plus` bundles `4.x`) causes two different Vitest majors to load side by side, visible as a `` `esbuild` option ... deprecated, please use `oxc` instead `` warning from `pnpm test`. Bumping the version and re-running `pnpm test` is enough to confirm; no config changes needed.
- `NCPD-Template-Child` does **not** use Nuxt — its `site-sample` is a plain Vite+Vue3 static site inside an AWS SAM/CloudFormation template, and its nested `src/app/` layout is an artifact of that repo being a multi-service AWS CDK monorepo. Don't assume anything in this repo's structure should mirror Child beyond "it's also Vite+Vue".
- GitHub Pages **does** need a one-time manual repo setting, despite `pages: write` in `gh-pages.yml`: the repo owner must visit Settings → Pages → Build and deployment → Source and pick "GitHub Actions" once. Verified by watching real run failures — with `actions/configure-pages@v5` at its default (`enablement: false`), the "Get Pages site" call 404s if Pages was never enabled; adding `enablement: true` gets further but then "Create Pages site" fails with `Resource not accessible by integration`, because creating a Pages site via the API needs repo-admin permission, which the default `GITHUB_TOKEN`'s `pages: write` scope does not grant. Once the owner enables Pages manually, `enablement`'s value stops mattering (`Get Pages site` just succeeds).
- For ad-hoc browser verification in a sandbox with no real Chrome install, use `npx @playwright/cli` (bin `playwright-cli`, an interactive/scriptable session CLI — distinct from the `playwright` library) with a config pointing `browser.launchOptions.executablePath` at `/opt/pw-browsers/chromium` and `args: ["--no-sandbox"]`; the default `chrome` channel isn't installed.
- `swipeable-item.vue`'s pointerdown handler must NOT call `setPointerCapture` (or otherwise claim the gesture) until real horizontal movement is confirmed — calling it unconditionally on every pointerdown silently breaks tapping the nested `RouterLink` (the click event stops reaching the link entirely, no error thrown), since the capturing element intercepts the events a native click would otherwise resolve against. Confirmed by adding a movement threshold (`SWIPE_ACTIVATION_PX`) before capturing; plain taps now pass through untouched.
- In this sandbox, `page.mouse.move()` calls issued back-to-back in a loop (even each individually `await`ed) can silently stop delivering events after the first one — not a bug in the page, verified by dispatching synthetic `PointerEvent`s directly via `element.dispatchEvent()` instead, which delivered every event as expected. Don't conclude a gesture handler is broken from a `page.mouse`-based Playwright test alone; cross-check with direct `dispatchEvent` before assuming a real bug.
- Reading `getComputedStyle(...)` (or any DOM state) immediately after firing events inside the same `page.evaluate()` call sees pre-render state — Vue batches reactive DOM updates on a microtask, which doesn't get a chance to flush until `evaluate()` returns to Node and the event loop turns over. Split "fire events" and "read resulting DOM" into two separate `page.evaluate()`/`page.waitForTimeout()` steps.
- Since `@cloudflare/vite-plugin` was added, `pnpm preview`/`vite preview` runs everything through workerd + the Worker's `fetch` (so `env.ASSETS.fetch()` serves the static files), not a plain static file server. It does **not** honor `VITE_BASE_PATH` the way GitHub Pages' real hosting does (Workers Assets maps the request path directly onto the built files, with no path-prefix awareness). To actually verify a `VITE_BASE_PATH=/DictaTube/` build the way GitHub Pages will serve it, symlink `dist/client` to a `DictaTube/` subdirectory under some root and serve that root with a plain static server (e.g. `http-server`) — don't rely on `vite preview` for this specific check.
- `wrangler login`'s OAuth flow needs a browser that can reach the CLI's local callback port — that never works from a remote/cloud sandbox. Real Cloudflare work (the step-0 Workers↔YouTube spike, D1, Access setup, verifying `*.workers.dev` + Access) has to happen from the owner's own machine.
- `deploy-production.yml` ([ADR-005](./docs/adr/005-develop-main-branch-deploy-split.md)) deploys via `cloudflare/wrangler-action@v3` + a `CLOUDFLARE_API_TOKEN` repo secret, not `wrangler login` — a scoped API token authenticates non-interactively, so this works from a GitHub Actions runner even though `wrangler login` itself never works from this sandbox (see previous Gotcha). That said, this workflow **cannot succeed yet**: `CLOUDFLARE_API_TOKEN` hasn't been added to the repo's secrets, and `wrangler.jsonc`'s `d1_databases[0].database_id` is still the placeholder `REPLACE_WITH_D1_DATABASE_ID` (no real D1 instance created yet). Both need the owner's own machine. Don't read a failing `main` push as a regression until both are done.
